摘要
本课程项目设计一个可视化任务编排器（Visual Task Orchestrator，简称 VTO）。用户输入或粘贴设计规格文本后，系统按规则自动把规格分解为任务清单，在画布上以节点—连线的有向无环图（DAG）形式编排任务依赖，一键执行并实时可视化运行状态，支持编排方案的保存、加载与导入导出。项目的主要目的不是实现真实的流水线执行器，而是把"规格→任务→编排→执行"的软件工程过程变得可见、可检查、可复用。
课程版采用 Vue 3、AntV X6、Express 与文件存储实现，前后端分离，通过 REST 接口通信。系统使用规则引擎完成可解释的任务分解，用模拟执行器完成任务执行（延时、失败注入、条件路由），不依赖任何外部服务，可离线演示。六名成员分别负责项目统筹、需求与规格、架构与后端、前端与交互、数据与接口、测试与配置管理。项目计划用六周完成需求分析、原型实现、测试和课程展示。
关键词： 软件工程；任务编排；可视化；DAG；规则分解
一、项目概述
1.1 项目背景
在软件工程实践中，从设计规格到可执行任务的传统拆解依赖人工与文档，缺乏可视化手段，导致三个问题：任务依赖关系不直观、执行进度不可观测、编排方案难以复用。学生小组在课程实践中也常遇到类似问题——任务拆解随意、依赖关系靠口头约定、执行过程不可见，成员难以判断某个任务为何这样安排，教师也不容易检查开发过程。
本项目把"设计规格→任务分解→画布编排→执行监控"放进一个可视化平台。系统保存每一步的结果，接入简单的 Git 协作流程，既体现可视化编排对工程实践的直接帮助，也覆盖软件工程课程强调的需求分析、模块设计、项目计划、配置管理和软件测试。
1.2 项目目标
课程版需要实现以下目标。
1. 用户可以粘贴文本或上传 .txt/.md 文件导入设计规格，系统自动识别 Markdown 标题与中文编号两种格式（验收标准 AC-01）。
2. 系统按规则把规格分解为任务清单，并给出依赖、并行与条件建议（AC-01、AC-02）。
3. 用户可在画布上拖拽节点、连线、编辑属性，非法连接被即时拒绝并提示（AC-03、AC-04）。
4. 用户点击执行后，系统完成方案校验、拓扑调度与执行，并行、条件分支、失败重试语义完整，运行状态实时可视化（AC-05～AC-08）。
5. 编排方案可保存、加载、导入、导出，刷新页面后数据不丢失（AC-09）。
6. 内置示例方案，全新用户五分钟内可完成首次编排演示，全程可离线运行（AC-10）。
本文档按"自包含"原则编写：数据契约、接口、算法与验收标准均给出精确定义，任一实现者（含 AI 辅助开发）仅凭本文档即可独立完成开发与自测，无需额外沟通。
1.3 项目范围
课程版面向单用户、本机或局域网运行环境，方案规模控制在 100 节点、200 边以内。执行语义为模拟执行（延时、失败注入、条件路由），不执行真实外部任务。
本期不实现多用户协同编辑、真实任务适配器（HTTP 请求、脚本执行）、WebSocket/SSE 推送（500ms 轮询已满足需求）和大模型辅助分解（规则引擎为基线方案）。以上内容列入成果说明书的展望方向，不作为课程验收的必要条件。
1.4 术语定义
术语 | 说明
编排方案（Plan） | 由若干节点与有向边构成的 DAG，描述一组任务的分解与执行编排，是系统的核心数据单元
节点（Node） | 编排图的基本元素，分为开始、任务、条件分支、延时、结束五种类型
边（Edge） | 节点间的有向依赖，从源节点出端口指向目标节点入端口
设计规格（Specification） | 描述系统功能与处理流程的文本，支持 Markdown 标题与中文编号两种格式
任务分解（Decomposition） | 将设计规格转换为任务清单及依赖、并行、条件建议的过程
波次（Wave） | 拓扑分层后同一层级的节点集合，层内节点相互无依赖，可并行执行
就绪队列（Ready Queue） | 所有入边均已定态的节点组成的待执行队列
执行上下文（Context） | 运行期间的变量表与节点输出集合，供条件表达式求值
定态（Settled） | 节点进入 SUCCESS、FAILED、SKIPPED、CANCELED 之一，不再变化
汇聚点（Join） | 入度大于 1 的节点，等待所有入边定态后执行

2.1 用户角色
平台主要面向两类用户。学生开发者（含项目组长）负责导入规格、编排画布、执行方案、复用与演示；课程教师或评审人员负责检查"规格→任务→验收"之间是否对应，并按第 8.4 节验收标准逐条验收。

2.4 主要使用场景
学生开发者打开编辑器，粘贴附录 A 的"用户登录功能"规格文本，点击"分解"后系统识别 Markdown 格式并生成任务清单表格，列出每个任务的类型、依赖与分支绑定。开发者微调后确认，系统按分层布局生成 10 节点 11 边的画布。开发者再从节点库拖入一个延时节点并连线，演示非法连接（自环、开始节点二出等）被即时拒绝。点击"执行"后，两级校验任务并行变蓝，条件分支按表达式路由，未激活分支变黄（SKIPPED），全部完成后变绿，底部日志与进度条同步更新。将某任务失败率调高后再次执行，可观察失败重试与下游跳过。最后保存方案、刷新页面、从方案列表重新打开，画布完全一致。教师按 AC-01～AC-10 逐条验收，并通过需求追踪表检查需求、任务、测试之间的对应关系。

四、总体设计
4.1 系统结构
系统采用前后端分离的分层架构：
┌───────────────────────────── 浏览器（前端）─────────────────────────────┐
│  视图层：工具栏 / 节点库面板 / 画布（AntV X6）/ 属性面板 / 运行面板 / 日志面板 │
│  状态层：Pinia（planStore / runStore）          │ 组件库：Element Plus    │
│  适配层：CanvasAdapter（画布↔数据双向同步、校验高亮、状态着色映射）          │
│  通信层：Axios（REST，JSON）                                                │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   │ HTTP / JSON
┌──────────────────────────────────┴───────────────────────────────────────┐
│                         Node.js + Express 服务端                          │
│  路由层：/api/decompose  /api/plans  /api/runs                            │
│  服务层：planService（保存/加载/导入导出）  runService（执行/查询/停止）      │
│  执行引擎（M3）：规格解析器 → 任务分解器 → 图校验器 → 调度器 → 执行器         │
│                （节点状态机 + 执行上下文 + 受限表达式求值）                   │
│  存储层：文件存储 storage/plans/*.json、storage/runs/*.json（原子写）        │
└───────────────────────────────────────────────────────────────────────────┘
核心数据流：规格文本 →（分解器）→ TaskSpec →（画布）→ Plan JSON →（校验器）→（调度器/执行器）→ Run 快照与日志 →（前端轮询）→ 状态可视化；Plan JSON 同时经存储层落盘。
设计原则：① 单一数据契约——编排方案 JSON 是画布、引擎、存储三方唯一事实来源；② 引擎与 UI 解耦——引擎只产出运行快照与日志事件，前端仅按状态映射着色；③ 校验前置——一切执行以前置校验为准，杜绝"边执行边出错"；④ 注册式扩展——节点类型、校验规则、表达式函数均可注册扩展；⑤ 渐进交付——先打通 P0 主链路（导入→分解→编排→执行→保存），再完善 P1/P2。

五、核心业务流程
5.1 五个阶段
1. 规格导入。 用户粘贴文本或上传文件，系统检查格式并识别 Markdown 标题或中文编号结构。完成条件是规格文本非空、格式可识别。
2. 任务分解与确认。 系统按规则生成任务清单（TaskSpec），用户在表格中勾选、改名、改类型、增删后确认。完成条件是每个任务都有类型、依赖与验收方式。
3. 画布编排。 系统按分层布局把确认后的清单生成节点图；用户继续拖拽节点、连线、编辑属性。完成条件是画布结构通过前端轻校验（唯一入口出口、无自环重复边等）。
4. 校验与执行。 用户点击执行，服务端全量校验（R1～R8）通过后按拓扑分层调度执行，状态与日志实时回传。完成条件是所有"必须"节点有执行结果。
5. 保存与复用。 方案保存到服务端，可重新加载、导入导出，内置示例可一键载入。完成条件是刷新页面后方案可完整恢复。
5.2 阶段检查
阶段 | 主要成果 | 进入下一阶段的条件
规格导入 | 规格文本、格式识别结果 | 文本非空且格式可识别
任务分解 | 任务清单 TaskSpec | 用户确认清单，每个任务有类型与依赖
画布编排 | 节点图 Plan（前端轻校验通过） | 通过前端轻校验，无悬空节点
校验与执行 | Run 快照、日志 | 必须节点完成，失败节点有原因记录
保存与复用 | 持久化方案、演示材料 | 保存后刷新重开一致，AC-01～AC-10 通过

5.3 任务分解规则
输入：设计规格文本，自动识别两种结构格式之一——Markdown 标题（#～####）或中文编号（"一、"、"1."、"1.1"）。
处理流程：
1. 清洗：去除空行、统一全半角、规范化缩进；
2. 结构识别：按标题/编号层级构建任务树（父—子关系）；列表项作为叶子任务；
3. 关键词映射（规则表）：
模式 | 动作
并行： / 同时 / 分别 | 该条目与其同级条目标记为并行组（parallelGroup）→ 生成 fan-out
如果 / 否则 / 判断 / 是否 | 生成 condition 节点
等待 / 延时 / 延迟 | 生成 delay 节点
结束 / 输出 / 提交 | 收敛到 end 节点
条目后缀 （通过时） / （未通过时） | 绑定到最近 condition 的 true / false 分支

4. 依赖推断：父条目 → 子条目建立依赖；同级条目默认按文档顺序串行；命中并行规则的同级组改为 fan-out（多出边）；
5. 输出：TaskSpec（6.5 节）返回前端供确认。
设计说明：采用规则引擎而非大模型——结果可解释、零外部依赖、便于编写测试断言；规则以数组注册，未来可扩展或接入 LLM 分解。完整示例见附录 A。
5.4 方案校验规则
编号 | 规则 | 检查内容
R1 | 唯一入口出口 | 恰 1 个 start（入度 0）与恰 1 个 end（出度 0）
R2 | 无环 | DFS 三色标记检测，有环时报告环上节点序列
R3 | 可达性 | 所有节点自 start 可达且能到达 end；报告孤立节点/悬空边
R4 | 条件汇聚 | condition 恰有 2 条出边（true/false 各一）；两分支必须汇聚于同一 join 节点（分别沿两分支 BFS，存在公共可达节点且该节点入度 >1）
R5 | 边合法性 | 无自环、无重复边、两端端口存在
R6 | 属性合法 | name 非空且 ≤50 字符；duration/wait ∈ [0,60000]；retry ∈ [0,3]；failRate ∈ [0,1]；expression 通过受限解析
R7 | ID 唯一 | 节点/边 ID 不重复
R8 | 结构一致 | 边两端节点均存在（防御数据损坏）

校验失败返回 { code: 40002, details: [{ nodeId, rule, message }] }，前端按 nodeId 定位高亮，属性面板下方列出错误清单，点击错误项定位并居中节点。前端在交互层预防大部分非法结构（R1/R3～R5 让错误"造不出来"），服务端校验始终是权威。
5.5 执行调度算法
1. 构图：由 nodes/edges 构建邻接表与入度表；
2. 校验：执行 5.4 节全量校验，不通过则拒绝执行；
3. 拓扑分层：Kahn 算法求每个节点的 level（波次），level 越大越晚就绪；同层节点无依赖关系，具备并行性；
4. 调度执行：维护就绪队列（所有入边定态的节点入队），信号量控制在途执行数 ≤ maxConcurrency（默认 3，可在方案 meta 覆盖）；队列与在途均空时进入终止判定；
5. 节点执行语义：
start：立即 SUCCESS；
delay：等待 wait 毫秒后 SUCCESS；
task：按 duration 模拟耗时；按 failRate 概率注入失败；失败且 retry>0 时按 500ms×attempt 退避重试；重试耗尽 → FAILED；成功且配置 output → 把 {变量名: true} 写入执行上下文；
condition：受限求值 expression → 激活 true 或 false 一侧出边；未激活一侧沿下游传播 SKIPPED，遇到 join 节点（入度>1）停止传播；
end：SUCCESS，进入收尾；
6. 汇聚（AND-Join）语义：入度 >1 的节点等待所有入边定态（SUCCESS 或 SKIPPED）；若任一入边 FAILED，本节点 SKIPPED 并继续向下传播（fail-fast；方案 meta 配 continueOnError=true 时忽略失败继续执行）；
7. 终止判定：所有节点定态后，存在 FAILED 则运行 FAILED，否则 SUCCESS；用户停止时未开始节点全部 CANCELED，运行 CANCELED；
8. 快照落盘：每次状态变化更新 Run 快照并追加日志（6.4 节）。
表达式文法（受限）：比较（==、!=、>、<、>=、<=）、逻辑（&&、||、!）、括号、上下文变量、数字/字符串字面量。自研 tokenizer + 递归下降解析器实现，禁止函数调用、赋值与任意 JS 执行（满足非功能需求"安全"项）。示例：passed == true && count >= 3。
执行上下文（Context）：{ variables: Record<string, boolean|number|string>, outputs: Record<nodeId, any> }；task 的 output 在成功后将 {变量名: true} 写入 variables。
5.6 节点与运行状态机
节点状态—颜色映射（画布与图例共用）：
状态 | 含义 | 节点颜色
PENDING | 未开始/等待依赖 | 灰 #d9d9d9
RUNNING | 执行中 | 蓝 #409eff
SUCCESS | 成功 | 绿 #67c23a
FAILED | 失败（重试耗尽） | 红 #f56c6c
SKIPPED | 分支未激活/上游失败跳过 | 黄 #e6a23c
CANCELED | 用户停止 | 深灰 #909399

状态流转：PENDING 在入边定态后进入 RUNNING；成功转 SUCCESS，失败且重试耗尽转 FAILED；用户停止时未开始节点转 CANCELED；条件未激活分支由 PENDING 转 SKIPPED 并向 join 传播。运行级状态机：IDLE → VALIDATING → RUNNING → SUCCESS / FAILED / CANCELED。
状态可视化：前端 runStore 每 500ms 轮询 GET /api/runs/:runId（带 since 增量参数），更新节点颜色、图例计数与进度条（定态节点数 / 总节点数）。日志面板展示结构化日志（时间、节点名、事件、消息），自动滚动到底部，失败行红色高亮。轮询可平滑升级为 SSE/WebSocket，查询接口不变。

POST /api/plans：请求完整 Plan JSON（无 id 新建，有 id 更新）；响应 200 { "id": "plan_ab3f9k", "updatedAt": "…" }；结构非法 40001。
POST /api/plans/:id/execute：响应 200 { "runId": "run_7x2pq" }；校验失败 40002 并附 details: [{ nodeId, rule, message }]；方案已在执行 40901。

POST /api/runs/:runId/cancel：响应 200 { "status": "CANCELED" }。
错误码 | 含义
40001 | 请求 JSON 结构非法
40002 | 编排方案校验失败（附 details 定位）
40003 | 规格解析/分解失败
40401 | 方案不存在
40402 | 运行记录不存在
40901 | 方案正在执行中
50000 | 服务器内部错误

前端模块间接口：planStore（Pinia）维护 nodes、edges、meta，提供 load/save/importPlan/exportPlan/undo/redo/autoLayout/setDirty/restoreDraft；runStore（Pinia）维护 runId、status、nodeStates、logs，提供 start/stop/poll（500ms 轮询，运行中自动调度）；CanvasAdapter（负责人 B）负责 X6 Graph 与 planStore 双向同步、选中态→属性面板、校验错误高亮、状态颜色映射，事件约定 node:selected、graph:changed、plan:validated。

实现一致性约束（开发时不得违反）：
1. 引擎不得依赖前端，不得感知界面渲染；只产出 Run 快照与日志事件；
2. 条件表达式禁止 eval / new Function，必须走 5.5 节白名单解析器；
3. 节点状态颜色以 5.6 节映射表为唯一来源，前后端共用同一份常量定义；
4. 一切执行以前置校验为准：校验失败时不得执行任何节点；
5. 所有加载/导入的 JSON 一律经过 Schema 校验，损坏文件给出友好报错而非崩溃。

九、进度与风险管理
9.1 进度安排
每周设置一次阶段检查。若某一模块延期，优先保证"导入→分解→编排→执行→保存"主链路，暂时裁剪动画、草稿恢复、导入导出等 P1/P2 功能，真实 AI 辅助分解一律缓做。项目组长每周检查一次风险和任务完成情况，风险关闭需要写明处理结果；不能用"后面再改"作为长期处理方式。出现严重范围问题时，由全组讨论调整计划，并保留调整记录。
9.2 主要风险
风险 | 影响 | 应对方法
AntV X6 API 学习曲线较陡 | 画布模块延期 | W2 预研最小 demo 先行；封装 CanvasAdapter 隔离 X6 细节
条件分支与汇聚（join）语义复杂 | 引擎行为分歧 | 本说明书 5.5 节精确定义语义；专项测试 R4、AC-05～AC-07
成员进度不一致导致联调阻塞 | 联调延期 | 接口先行、JSON 契约冻结、按里程碑兜底

十、总结
本课程项目把"设计规格→任务分解→画布编排→执行监控"的软件工程过程放进一个可视化平台。平台将规格、任务、依赖关系、执行状态、日志和测试记录连接起来，使任务编排过程能够被查看和检查。课程版不追求真实的流水线执行能力，而是用较小的技术范围展示需求分析、模块设计、团队协作、配置管理和软件测试。
项目完成后，小组应能够演示一条完整链路：导入规格、分解确认、生成画布、编辑编排、执行方案、查看状态与日志，并说明相关代码所在分支和提交。这些内容能够对应本科软件工程课程的主要考核点，也便于教师在有限时间内检查项目过程。

"并行："命中并行规则 → 校验用户名格式、校验密码非空同组 fan-out；
两级校验均为"查询用户信息"的前置 → 生成 join（入度 2）；
"判断："命中条件规则 → condition（表达式 passed == true，变量由"比对密码哈希"的 output 提供）；
"（通过时）/（未通过时）"绑定 true/false 分支；"输出登录结果"收敛为 end（两分支汇聚）。
