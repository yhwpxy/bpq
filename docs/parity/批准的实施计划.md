## 4. 架构与兼容方案

### 4.1 数据和接口

1. 保留旧 `version: "1.0"` 作为数据格式版本；发布版本另用 `versionId`、`versionTag` 表示。
2. WBS 与执行图共享规范化节点标识；父子层级、前向依赖和返工边分别建模，使用同一执行核心。
3. 旧 TaskSpec 接口继续遵守原有严格字段契约。新增 GoalSpec 与规划接口，避免破坏已有响应和非法字段检查。
4. 保留模拟执行器、失败注入、原始示例和原表达式语义；真实执行通过新增适配器接入。
5. 所有新运行绑定版本。旧执行入口通过兼容流程建立快照；完整新工作流走校验、试运行、发布流程。
6. 版本快照仅创建、不覆盖；运行状态、attempt 与审计在运行锁内一致更新；JSON 索引可重建。
7. 设计草稿与运行图分离。GhostNode 只改变运行图；不允许借运行操作修改发布版本。
8. 保留既有增量日志契约，扩展审计事件与游标，验证断线补拉、去重和顺序。
9. 真实执行和凭据管理接口启用时同步加入本地鉴权，不等到最终发布才保护这些接口。

### 4.2 新语义纳入 R1～R8

| 规则 | 保留职责 | 扩展职责 |
| --- | --- | --- |
| R1 | 唯一开始/结束、端口约束 | 执行入口、终点和非执行层级容器边界 |
| R2 | 拒绝普通环 | 显式返工范围、上限和恢复语义；任意标成 loop 不得绕过检查 |
| R3 | 可达性 | 条件与失败恢复路径的可达性 |
| R4 | 条件分支及汇合 | 新路由类型、默认路径、Join 屏障 |
| R5 | 自环、重复边、端口 | 前向、失败及返工边的合法连接类型 |
| R6 | 属性与表达式 | 契约、能力、资源、权限、命令策略与 DDD 子诊断 |
| R7 | ID 唯一 | WBS、需求、版本及运行实体标识一致性 |
| R8 | 悬空引用 | FR/AC、能力、父节点、检查点、版本归属与覆盖引用 |

新增诊断使用子码和 Error/Warning/Info，不另建可绕过 R1～R8 的验证入口。旧图普通环、start 单出边、表达式安全等约束继续有效。

### 4.3 不复制参考实现中的不足

- 补齐 AC 覆盖与上下游契约兼容，不能仅检查字段非空。
- 持久化真正的 Task → Subtask 层级，不能只显示 Phase 和扁平任务。
- 校验与试运行报告绑定草稿内容摘要，修改后失效，不能复用过期通过结果。
- 恢复前保存未提交及未跟踪产物的可恢复状态，不能只保存 HEAD 后清理文件。
- MCP 只依据真实探测结果展示状态，不能因匹配演示地址就返回成功。
- 离线演示产物明确标识；真实 QA 不能采用固定分数和固定通过结果。
- 费用统计依据 usage 与配置费率；预算展示不等同于供应商账单的硬上限保证。

### 6.2 核心演示链路

1. 导入需求 → 核对 GoalSpec 与来源 → 确认建议 → 查看三级任务树和规划理由。
2. 修改表单或画布 → 查看影响分析 → 修复三级诊断 → 隔离试运行。
3. 发布 v1.0 → 启动运行 → 修改草稿并发布 v2.0 → 验证旧运行仍绑定 v1.0。
4. 并行执行 → 条件分支跳过 → Join 汇合 → 人工门禁 → 暂停恢复。
5. 工具门禁失败 → 检查点恢复 → 有界返工 → 查看恢复前证据及 attempt 历史。
6. 运行期插入 GhostNode → 补充任务执行 → 发布版本保持不变。
7. 查询节点、会话、审批和返工记录 → 增量补拉 → 搜索 → 导出 evidence 文件。
8. 切换中英文 → 配置能力、MCP、DDD 和工程规则 → 检查健康、费用和环境诊断。

### 6.3 外部条件与验证边界

- 基础环境：Node、npm、浏览器；真实工作区执行还需要 Git 和可写磁盘。
- 本地工具任务：目标命令及其依赖必须安装；测试使用临时仓库和可控命令。
- 真实模型：需要有效的服务地址、模型名称、Key 和网络；自动化测试使用本地协议替身。
- CLI/ACP：真实联调需要对应可执行程序及授权环境；协议替身通过不能冒充第三方真实联调通过。
- MCP：连通性探测需要可访问的 HTTP 服务或本地程序；可达不等于完成 MCP 工具调用。
- 不能把文件路径检查和 worktree 隔离描述为操作系统级强沙箱；运行边界按实际实现说明。
- 未验证的环境、未完成的能力和估算费用必须标识，不写成已经通过。

## 7. 分支、提交与推送规则

1. 确认本计划后，从远端 main 的核定基线创建 `feat/parity-with-reference`，所有实施改动在该分支完成。
2. 每完成一个模块提交一次，commit message 写清模块与验收点，不直接提交或推送 main。
3. 每次模块推送前，在待推送提交对应状态依次运行以下四项，全部成功后才允许推送：

   ```bash
   npm ci
   npm test
   npm run build
   npm run test:e2e
   ```

4. 任一项失败，修复并重新验证；测试通过后若又修改代码，必须重新验证待推送状态。
5. 使用普通 `git push`；禁止 force push、改写历史、删除远程分支。
6. 创建并维护同一个 PR，逐模块附：改动文件清单、新增测试数量、四项检查结果和日志摘要；关键界面链路附截图。
7. 不因 PR 已创建而宣称模块完成。功能、测试和证据必须同时满足验收。
8. 遇到无法在约定技术栈内完成的功能，停止该模块，在 PR 写明阻塞原因、影响和替代方案，不虚构结果。
