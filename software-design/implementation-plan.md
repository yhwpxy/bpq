# 通用软件设计阶段 · 实现与验收方案

设计服务应对接一个固定的上游类型和一个固定的下游类型，中间的模块数量、业务实体、接口形式和验证方法由本次需求推导。接入新领域时，用户提供想法与材料，工程团队绑定目标工作区，即可沿用同一套生成、评审、确认和交接流程。

## 1. 当前能力与接入位置

| 边界 | 仓库现状 | 拟做的集成 |
| --- | --- | --- |
| 用户输入 → PRD | HAMA 的 live 路径向所选模型发送本次任务数据，demo 路径才调用预设 responder。确认后的基线带 projectId、版本、审批与稳定需求编号 | 继续使用现有输入与确认流程；按 baselineId 加载本次发布内容，用户无需选择行业模板。[Agent 调用](../requirements-engineering/src/agents.ts) · [基线服务](../requirements-engineering/src/service.ts) |
| PRD → 设计 | 现有直接交接在 HAMA 服务中拼装 GoalSpec。工作流中另有架构规划与契约任务 | 在需求页增加“生成软件设计”，工作台先明确选择目标工程，再显示设计草案、来源及待决问题。保留现有导入操作供已有调用方使用。[需求页](../workflow-orchestrator/renderer/src/views/RequirementsView.tsx) · [宿主路由](../workflow-orchestrator/src/server/http-router.ts) |
| Design Spec → 现有 PM Agent | Planner 的 importStructuredRequirements 接受结构化 GoalSpec 并调用 decomposeStructural | 确认时冻结设计；交接时按确认版构造输入并核对返回的 GoalSpec、工作流 ID 和 PM 报告。任务分解由现有 PM 完成。[Planner](../workflow-orchestrator/src/engines/planner.ts) · [PM Agent](../workflow-orchestrator/src/engines/pm-agent.ts) |

## 2. 如何从本次输入推导设计

1. **读取事实。** 由服务组装 `{baseline, workspace, sourceCommit, inventory, reviewFeedback}`。基线提供场景、功能、质量目标、依赖和 Given/When/Then 验收。inventory 以工程相对路径记录入口、可复用组件、运行约束和验证命令来源。设计生成只读取当前项目选定的材料，示例文件由演示或测试入口显式选择。
2. **找到变化点。** 对每个原始 requirementId，列出触发者、输入、已有行为、期望结果以及关联 AC。新工程从最小交付路径起草；已有工程以现有入口和调用方为起点，补充兼容性、存量数据或迁移影响。只有性能改进的需求也可以只修改已有模块，并以 PRD 认可的负载和测量条件验收。
3. **划定模块与契约。** 按职责、数据所有者、依赖及可独立验证的边界合并变化点，并把每项决策回指到原需求或工程证据。每个模块声明文件范围；每条跨模块依赖给出提供方、消费方和契约。库可以只有函数接口，批处理工具可以只有文件输入与命令行输出。模块数由实现决定。
4. **处理未知。** 缺少技术信息时，记录问题、关联需求、受影响决策、可选方案和核验方法。可以继续设计已确定部分。若未知项会改变用户目标或通过标准，返回 HAMA 澄清或变更基线；若影响实现，则在设计评审解决。只在所需事实有依据后确认对应修订。
5. **确认并传入 PM。** 对照原始 PRD 检查设计覆盖、文件范围及验收语义，冻结确认稿。交接适配器将完整正文及模块投影到 GoalSpec，调用现有 Planner。以返回的 goalSpec 核对实际入参，以 pmReport 核对 PM 收到的模块与需求引用；保留基线、设计及报告的关联。

## 3. 分期实施

| 次序 | 工程变更与产物 | 完成判据 |
| --- | --- | --- |
| 1 · 契约与生成 | 在 software-design 下新增领域类型、结构校验、设计服务及 Markdown 渲染；在宿主 runtime 装配。复用 CapabilityHub 的文本调用方式，单独定义设计输出 schema 和提示。模块、边界、决策、追踪、未决事项均为基于输入生成的集合 | 给定不同基线，同一个生成入口返回各自的需求、路径和契约；模型输出非法、引用悬空或调用失败时保留诊断并支持重试 |
| 2 · 评审与持久化 | 接入设计修订、决定、交接关联三类记录及设计端点。在工作台显示基线、目标仓库、逐项覆盖、版本差异及退回理由 | 可从待审草案退回并形成新修订；旧摘要无法批准新正文，重启后能继续原评审 |
| 3 · 现有 PM 接入 | 按确认修订生成结构化输入，复用 importStructuredRequirements，并将交接记录与工作流落库协调为一次提交 | 回读正文与确认稿一致，报告的 workflowId 与返回工作流匹配、detectedModules 与设计一致；重复提交返回原回执 |
| 4 · 跨项目验收 | 用不同项目的 PRD 验证同一套转换规则，再选一个真实基线与目标工作区验证 PM 签收 | 每条原始需求和 AC 可回查，设计决策及文件范围因项目而异；保存 PRD、确认设计与接收报告 |

结构定义与交接契约见[子系统设计说明](./subsystem-design.md)，逐项联调见[实施清单](./checkoutlist.md)。下表中的预期业务结果用于检查 Design Spec 是否给出了可验证的实现方案。

## 4. 如何验证可以换需求

| 输入与来源 | 应随需求变化的输出 | 可观察的验收结果 |
| --- | --- | --- |
| 移动活动报名，来自仓库 HAMA 演示 | 移动界面、报名 API、容量状态与重复写入约束 | 保持原始 4 条需求的追踪，末席并发和小屏操作分别有验证方法。[演示来源](../requirements-engineering/src/demo.ts) |
| 多币种清算，来自编排器自带账本 Design Spec | 分录、汇率快照、对账回调三个模块；使用金额最小单位、平衡规则和报价有效期 | 现有预设可独立验证下游拆解。验证生成服务时，另建含上述业务事实的测试基线，仅把基线和目标工程交给生成器，检查其产出是否覆盖平衡与过期报价验收。[预设来源](../workflow-orchestrator/src/core/presets.ts) |
| 新提出的命令行需求：统计 UTF-8 文本的非空行数，忽略纯空白行；输入不存在时以非零状态退出 | 文件输入、逐行判定、标准输出与退出码；可在一个现有命令模块中实现。此条为测试设计用例 | 输入依次为一行文字、一行空白、一行文字，标准输出为 2；文件不存在时检查退出码。检查生成物只引用该项目的需求和路径 |

再对同一个命令行项目更改需求，令纯空白行也计数。新版设计应指出判定逻辑、验收数据及预期值的变化（同一输入变为 3），保留文件错误处理的追踪。按两份 PM 回执分别取回对应的确认稿，核对项目与版本隔离。
