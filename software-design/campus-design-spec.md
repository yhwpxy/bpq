# 教学案例 · 校园服务平台移动端活动报名

## 目标

学生使用已有校园身份，在手机上查看活动、报名和取消。即使多人同时竞争最后一个名额，成功报名人数也必须在活动容量以内。

## 输入

- 现有校园登录会话，从服务端会话解析学生标识。
- 现有活动列表提供的活动标识、名称、可报名状态和容量。

## 输出

- 移动活动列表，显示余量、本人报名状态及可用操作。
- 报名和取消的服务端结果、更新后的报名状态及剩余名额。

## 需求

- FR-01 浏览活动，列表显示可报名活动及本人的报名状态。
- FR-02 报名或取消，同一学生重复提交后只保留一条有效报名。
- FR-03 确认报名时校验容量，最后一个名额只允许一人取得。
- FR-04 移动端易用，360 CSS 像素宽视口上可以完成报名。

## 模块

- 移动界面: 渲染列表、报名和取消按钮及失败提示，按服务端结果刷新；响应丢失后重新读取状态。覆盖 FR-01、FR-02、FR-04 (`src/mobile/activities/**`)
- 活动 API: 从校园会话取当前学生，提供活动列表 GET 和本人报名资源的 PUT、DELETE；未登录返回 401，满额的新报名返回 409。覆盖 FR-01、FR-02、FR-03 (`src/api/activities/**`)
- 报名持久化: 同一事务串行处理同一活动的写入；先查本人有效记录，再判断余量；重复取消只释放一次。覆盖 FR-02、FR-03 (`src/store/registrations/**`)

## 约束

- 复用现有校园登录和活动列表；首版范围排除候补队列。
- 文件范围是目标校园应用的拟定目录，正式拆解前须映射到实际仓库。
- 验证命令取目标工作区中实际运行对应测试的命令。

## 领域规则

- 活动和学生的组合标识唯一。有效报名数等于该活动的报名记录数，余量等于容量减有效报名数。
- PUT /activities/{id}/registration 设置本人的有效报名，DELETE 同一路径取消。相同操作重放后报名状态一致。
- 先锁定活动行，再检查本人记录和人数，新增或删除记录后提交；写入失败则回滚。

## 验收

- AC-01 FR-01 存在可报名活动时，学生打开列表能看见该活动及其报名状态。
- AC-02 FR-02 有余量且尚未报名时，连续提交两次报名，只产生一条有效记录。
- AC-03 FR-03 两名不同学生同时请求最后一个名额，仅一人成功，另一人看见名额已满。
- AC-04 FR-04 在 360 CSS 像素宽视口上打开页面，无横向滚动且能完成报名。
- AC-05 FR-02 设计补充检查：唯一报名者连续取消两次，最终无有效记录，余量只恢复一个。

## 假设

- 目标校园平台允许读取已有登录会话和活动列表，所用关系数据库支持事务、唯一约束及活动行写锁；接入时核实。
- 本例沿用校园演示的业务范围；演练导入后通过配套追踪表核对上游编号。
