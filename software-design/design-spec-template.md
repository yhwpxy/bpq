# 通用 Design Spec 编写模板

从本次已确认的 PRD 开始填写。每条需求先记录原始编号、业务规则和验收条件，再写实现该行为的模块、契约与技术决策。评审并确认同一修订后，用完整正文及结构化字段传给现有 PM Agent。下列尖括号表示待填写内容。

## 一、评审稿

| 项目 | 填写内容 |
| --- | --- |
| 标题与状态 | 〈本次交付的用户可见结果〉，〈草案／待评审／已确认〉，〈设计修订〉 |
| 来源与目标 | 〈projectId、baselineId、revision、sha256〉，〈目标工作区与提交〉，〈已有工程改造／新建工程〉 |
| 目标与范围 | 〈谁在何种条件下完成什么操作，或哪个系统消费什么结果〉。保留 PRD 的范围外事项 |
| 现有基础 | 〈已存在的入口、接口、文件、技术栈和测试〉及证据路径。新建工程填写已知约束并标明拟新增工件 |
| 方案决策 | 〈需求或工程约束〉→〈选用的实现〉→〈理由与代价〉。重大决定记录备选和改变决定的条件 |
| 执行顺序 | 〈触发入口〉→〈处理步骤〉→〈可观察结果〉。写明失败在哪里发生、调用方看见什么、是否保留部分结果 |

逐项填写下列明细。一项需求可落到多个模块，同一模块也可支撑多项需求。只有 PRD 或目标工程确实涉及共享状态、长期存储、身份、外部服务或性能目标时，才展开对应设计。

| 明细 | 每条应填写的字段 |
| --- | --- |
| 模块 | 名称、单一职责、输入与输出、依赖模块、目标文件范围及现有／拟新增标记、关联的原始需求 ID |
| 接口 | 双方、触发方式、输入类型及边界、输出结构、错误语义、可观察副作用。可写函数、命令、文件、事件或 HTTP 契约 |
| 数据 | 数据所有者、格式、来源与生命周期。需要存储时补主键、约束、迁移及一致性；纯计算可记录内存中的中间表示和释放时机 |
| 非功能要求 | PRD 原文、适用模块、观测方法与判定条件；缺少指标时保留待确认项 |
| 追踪 | 原始需求 ID、原始 AC ID、PM 短编号（仅 Markdown 需要）、负责模块、验证步骤与预期证据；设计补充检查标明来源 |
| 评审 | 设计修订与摘要、待定事项及责任人、决定与理由、处理结果和确认人；字段值由实际评审产生 |

## 二、供现有 PM 导入的正文

复制下面代码块的**内部正文**，替换全部占位符，按实际条目数增删各行。模块名称后保留冒号和空格，目标仓库相对路径使用反引号。每条需求、模块和验收各占一行，模块显式引用所有负责的 FR 短编号。验收行用可观察结果描述通过条件；反引号在此处有“验证命令”的特殊含义。输入、输出、验收均应明确，避免解析器自动补入泛化内容。[解析规则](../workflow-orchestrator/src/core/spec-parser.ts)

````markdown
# 〈项目名称与本次变更〉

## 目标
〈当前基线要求达成的结果〉

## 输入
- 〈实际输入材料、运行时数据或前置条件〉

## 输出
- 〈用户或外部系统能观察到的交付物〉

## 需求
- FR-01 〈来自已确认基线的一条功能或质量需求〉

## 模块
- 〈模块名称〉: 〈职责、边界与依赖〉，覆盖 FR-01 (`<相对目录>/**`)

## 约束
- 〈当前项目需要遵守的技术、兼容性或交付约束〉

## 领域规则
- 〈来自该项目的业务规则或数据不变量〉

## 验收
- AC-01 FR-01 〈给定输入和初始条件，执行操作后的预期结果〉

## 假设
- 〈待验证事实、影响及确认方式〉
````

没有适用内容的可选小节可删除。Markdown 中的 FR、AC 短编号与原始编号在评审稿内对应；正式结构化交接使用基线原始编号。填写后的正文可以在现有工作台导入，模板文件本身供作者编辑。
